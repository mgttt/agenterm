# Precision audit — narrow, high-confidence findings

Tracks a targeted second-pass review running alongside the ongoing
frontend-parity refactor. Scope is deliberately narrow: real correctness/
safety bugs and untested trust boundaries with limited, well-understood
blast radius — not architecture or style cleanup (that's covered by the
existing `plan-v0.1.13.md`/`ARCHITECTURE.md` tracks).

Process: investigate one item at a time, avoid files another agent has open
(check `git status` first), verify with `cargo check`/`clippy -D warnings`
(and tests where the host target allows), commit each landed item
separately, then update this table.

| 4 | IPC trust-boundary logic has zero unit tests | `src/control_authority.rs` (313 lines: admit/complete/finish_submission, replay/idempotency) | **Audited, no bug** | The underlying `ReplayWindow` state machine (`control_contract.rs`) is actually thoroughly tested (10+ cases: replay, conflict, expiry, eviction, completion validation, accepted-enrichment, serde roundtrip) — the earlier "zero tests" framing was about the thin `ControlAuthority` orchestration layer only. Traced its one call site (`server_app.rs:1431-1464`): `wait` is derived from the same `response.ok` passed into `complete()`, so the `wait.is_some() => Accepted` override can't fire on a failed response. `admit()`'s identity/fingerprint check recomputes both from the server-received `args` independently of client-supplied `control` metadata, so it's tamper-evident by construction. No bug found; not forcing test-only churn without one. |
| 5 | Reentrant `window_proc` aliases `&mut State` | `crates/agenterm-platform/src/adapters/windows/control_window.rs` | **Fixed** (pending commit) | Confirmed reachable chain: `WM_TIMER` → `dispatch` → `RemoteWindowApplication::event` (`src/platform/adapters/windows/remote_frontend.rs:6170`) → `state.tick()` → `process_client_command()` → `execute_client_command()` → a `"window-minimize"`/`"window-maximize"`/`"window-restore"`/`"window-resize"` command → `Backend::set_presentation`/`set_client_size` → `ShowWindow`/`MoveWindow` on the *same* `hwnd`. Win32 delivers the resulting `WM_SIZE`/`WM_WINDOWPOSCHANGED` synchronously, reentering `window_proc` while the outer call still holds `state` live via `&mut *state_ptr` — the reentrant call deref's the same raw pointer into a second, aliasing `&mut State`. This is exactly the hazard `Backend::close()` already defends against (it posts `DEFERRED_CLOSE` instead of calling `DestroyWindow` synchronously) — `set_presentation`/`set_client_size` just never got the same treatment, so the codebase demonstrates it already knew about this class of bug and applied the fix inconsistently. A thread-local `DISPATCHING` guard now makes any reentrant message fall back to `DefWindowProcW` instead of re-entering the state dispatch (checked before creating the `&mut State` alias, so `WM_NCDESTROY`'s `GWLP_USERDATA` cleanup was hoisted above the guard so it always runs). This keeps `set_client_size`'s synchronous `Result` contract intact (no caller-visible change), unlike deferring it the way `close()` does. Verified natively on this Windows host: `cargo check`/`clippy -D warnings` clean, and all 223 `agenterm-platform` unit tests pass, including the live-window `selected::control_window::tests::*` suite. Not verified: an actual end-to-end repro of the reentrant path running the shipped GUI (would need to drive `agenterm-cli.exe window-minimize` against a live `agenterm.exe`); recommend a manual or CI smoke pass before release. |
