# Precision audit — narrow, high-confidence findings

Tracks a targeted second-pass review running alongside the ongoing
frontend-parity refactor. Scope is deliberately narrow: real correctness/
safety bugs and untested trust boundaries with limited, well-understood
blast radius — not architecture or style cleanup (that's covered by the
existing `plan-v0.1.13.md`/`ARCHITECTURE.md` tracks).

Process: investigate one item at a time, avoid files another agent has open
(check `git status` first), verify with `cargo check`/`clippy -D warnings`
(and tests where the host target allows), commit each landed item
separately, then update this table.

| 5 | Reentrant `window_proc` aliases `&mut State` | `crates/agenterm-platform/src/adapters/windows/control_window.rs` | **Fixed** (`20144a1`, refined by `7c7409e`/`7dead17`) | Confirmed reachable chain: `WM_TIMER` → `dispatch` → `RemoteWindowApplication::event` (`src/platform/adapters/windows/remote_frontend.rs:6170`) → `state.tick()` → `process_client_command()` → `execute_client_command()` → a `"window-minimize"`/`"window-maximize"`/`"window-restore"`/`"window-resize"` command → `Backend::set_presentation`/`set_client_size` → `ShowWindow`/`MoveWindow` on the *same* `hwnd`. Win32 delivers the resulting `WM_SIZE`/`WM_WINDOWPOSCHANGED` synchronously, reentering `window_proc` while the outer call still holds `state` live via `&mut *state_ptr` — the reentrant call deref's the same raw pointer into a second, aliasing `&mut State`. This is exactly the hazard `Backend::close()` already defends against (it posts `DEFERRED_CLOSE` instead of calling `DestroyWindow` synchronously) — `set_presentation`/`set_client_size` just never got the same treatment. My initial fix (`20144a1`) added a thread-local `DISPATCHING` guard that dropped reentrant messages to `DefWindowProcW`, correct but lossy (a reentrant `WM_SIZE` would only be reconciled on the next poll tick). A follow-up commit (`7c7409e`, cleaned up by `7dead17`) improved this: reentrant messages are now queued (`PENDING_MESSAGES`) instead of dropped, and replayed through the normal state-dispatch path in a drain-until-empty loop once the outer dispatch has returned and released its `&mut State` — no aliasing (each replay is a fresh, non-overlapping reborrow after the earlier one is out of scope) and no lost messages. `WM_NCDESTROY`'s `GWLP_USERDATA` cleanup stays hoisted above the guard so it always runs regardless of dispatch depth. Re-verified on this Windows host after the follow-up: `cargo check`/`clippy -D warnings` clean. Not verified: an actual end-to-end repro of the reentrant path running the shipped GUI; recommend a manual or CI smoke pass before release. |

| 8 | Unbounded per-stream drain thread spawn | `src/script_stream.rs` (`from_reader_inner`, L122-205) | Found, needs a design decision before fixing | Confirmed the indirect bound does **not** cover every caller: `from_reader_inner` spawns one dedicated OS thread per stream unconditionally, with no cap anywhere in this file. `script_process.rs` uses it for child stdout/stderr, which *is* indirectly bounded by `worker_supervisor`'s process concurrency caps (8 global / 2 per-process, per the earlier Rhai-runtime review) — but `script_http.rs:348` also calls `from_bounded_reader` for every HTTP response body, and HTTP requests are **not** gated by that same limiter. A script that fires off many concurrent slow HTTP transfers (or just loops issuing requests without bounding concurrency) can spawn unboundedly many blocking OS threads, one per in-flight transfer, each held alive for the transfer's full duration (a thread only exits at EOF/error/cancel, independent of whether the script still holds the `Stream` handle — `ScriptStream::Drop`'s eager-cancel-on-last-reference behavior helps for abandoned handles, but does nothing for handles a script is legitimately still using). This is a real gap in exactly the "robustness budget" category AGENTS.md says should exist independent of the (intentionally unrestricted) capability itself — the same way `worker_supervisor` already caps concurrent worker processes. **Not implementing without a steer**: a correct fix means threading a `Result` through `from_reader_inner`/`from_reader`/`from_bounded_reader`/`from_process_stdout`/`from_process_stderr` (all four call sites in `script_process.rs`/`script_http.rs` would need new error handling), and picking a concrete concurrency limit is a product decision, not something implied by the existing code — the 8/2 worker-process figures are a different resource dimension and don't transfer. Flagging for a decision on the limit and the failure mode (typed error vs. blocking backpressure) before touching it. |
